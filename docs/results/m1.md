# M1 results

Machine: Intel Core i7-13700H, 13.7 GB RAM, Windows 11, Go 1.26.10 (windows/amd64). Six other
builds shared the machine during these runs, so the wall-clock times below are single observations.

All local runs use the in-process store (`internal/memkv`), which follows etcd's lease and revision
rules. No etcd cluster runs on this machine (no Docker, no multi-node runs locally); the real-etcd
tests run only in CI and **have not run yet**.

## Commands

```bash
gofmt -l cmd internal && go vet ./... && go vet -tags etcd ./...
go test -p 2 -count=1 -v ./...     # 41 tests, 20 subtests (make test adds -race; see below)
bash scripts/vulncheck.sh          # govulncheck@v1.8.0 (make audit)
go run ./cmd/distributed-lock-service demo     # make bench / make demo
bash .tmp/api_run.sh               # serve on 127.0.0.1:18090 and exercise the API with curl
bash .tmp/check.sh                 # all checks plus the portfolio audit; prints CHECK PASS
make test-etcd                     # CI only: DLS_ETCD_ENDPOINTS of a three-member etcd cluster
```

The backend contract (`internal/kv/kvtest`, 10 cases) runs twice locally: on memkv directly and on
the etcd client through a fake JSON gateway backed by memkv. The cases: grant, keep-alive and revoke;
create-if-absent once; every create gets a new revision; create revisions only increase across
delete and re-create; create needs a live lease; delete only by the holding lease; revoke deletes
attached keys; a lease expires without keep-alive; keep-alive extends a lease; oversized keys are
rejected. In CI the same contract runs against real etcd with `time.Sleep` as the clock.

## Measure: the demo (`make bench`)

In-process store, 8 clients, 25 rounds each, TTL 300 ms (recorded run, `docs/proof/demo.jpg`):

| Scenario | Result |
|---|---|
| Contention | 200 acquisitions of one lock by 8 clients; 0 overlaps; tokens 2 to 400, strictly increasing in acquisition order; wait p50 rounds to 0 s (lock free on the first try), p99 75.8 ms |
| Renewal | Holder kept the lock for 1.5 s (5 TTLs) with keep-alives; another client tried 50 times, 0 succeeded; still valid at the end |
| Crash | Holder stopped renewing without releasing; a waiting client acquired after 304 ms (TTL 300 ms); token 404 to 406 |
| Outage | Keep-alives failed (injected); the holder saw `ErrLost` after 303 ms (TTL 300 ms) and `Valid()` was false |
| Verify | `overlaps=0 token_regressions=0 renewal_steals=0 missed_loss=0 late_takeover=0 leases_left=0`, 2.262 s total |

An earlier run of the same command gave p99 105 ms and identical verify counts; the p99 wait depends
on scheduling on a shared machine.

HTTP API on 127.0.0.1:18090 with curl (`docs/proof/api.jpg`): acquire 200 (token 2, lease 1); a
second owner 409 with the holder; keep-alive 200 (`ttl_ms` 3000); release 204; the second owner then
acquires with token 4; keep-alive on the released lease 404 `lease_not_found`; an owner with a space
400.

## Analyze

- Takeover after a crash took 304 ms with a 300 ms TTL. The successor can only win after the store
  expires the lease, which is one TTL after the last renewal (at most TTL/3 before the crash), plus
  the waiter's polling delay (capped at 20 ms in the demo).
- The holder noticed loss after 303 ms: its deadline is counted from the *sending* time of its last
  successful keep-alive, so it ends no later than the store's lease does.
- Defects found while building M1:
  - **`Valid()` was briefly false right after acquisition.** The first version set the deadline
    inside the renewal goroutine. Fix: the deadline is set before the goroutine starts.
  - **Concurrent `Release` calls could close the stop channel twice.** Fix: `sync.Once`.
  - Two hand mutants survived the first test set (see the quality doc): a store that does not raise
    the revision on create (hidden because deletes raised it), and `Valid()` ignoring the deadline
    (hidden because the renewal goroutine ends the lock at the deadline). Both now have tests.
- govulncheck with Go 1.26.10 reports GO-2026-6859 (net/http, fixed in Go 1.26.11), reachable
  through the HTTP server and the etcd client. `scripts/vulncheck.sh` allows exactly that ID and
  fails on any other.

## Improve

- Deadline set at construction and `sync.Once` around the stop channel (above).
- New tests: `EveryCreateGetsANewRevision` (contract) and
  `TestValidIsFalsePastTheDeadlineBeforeRenewalsGiveUp`; both kill the mutants that survived.

## Control

- CI `build` job: gofmt, `go vet` (also with the `etcd` tag), `go test -race`, `scripts/vulncheck.sh`,
  and the demo, whose `verify:` line is printed as a `::notice` (`::error` and a failed job on any
  violation).
- CI `etcd` job: downloads etcd v3.6.4, checks it against the release's SHA256SUMS, starts three
  members on localhost and runs `make test-etcd`; the result is printed as a `::notice`.
- Any new store must pass the shared contract in `internal/kv/kvtest`.
